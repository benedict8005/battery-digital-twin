# Changelog (v1 to v10)

This notebook rebuilds the original Databricks PINN battery digital twin pipeline, with twenty fixes applied:

1. **Cell 11 (feature engineering):** logs how many cycles are skipped and why, instead of silently dropping them.
2. **OCV model:** replaced the crude linear `U_ocv = 2.7 + 0.015 * SoC` with a fitted empirical curve that captures the nonlinear knees near 0% and 100% SoC.
3. **`log_A_sei` persistence:** the learned Arrhenius pre-exponential factor is now saved *with* the network checkpoint and restored at inference time, instead of resetting to its untrained default.
4. **Inference-time architecture reconstruction:** reuses the real physics PDE (instead of a `dummy_pde` placeholder) when rebuilding the network for weight loading, with an explicit note on what `model.predict()` does and does not enforce.
5. **GPU-native interpolation:** `get_real_time_physics` no longer round-trips through `scipy.interp1d` on the CPU for every PDE residual call — it now uses a `torch.searchsorted`-based linear interpolation that stays entirely on-device.
6. **Ambient temperature as a model input:** `ambient_temperature` (previously dropped before `final_pinn_training_data`) is now carried through the pipeline and added as a 5th input dimension `[space, SoH, Re, Ambient, time]`. `T_delta` is re-referenced per-battery against its own ambient condition instead of a single global `T_ref = 25°C` — this addresses the diverging PDE residual losses (`loss_comp_0`/`loss_comp_1` climbing over training) observed in the MLflow run, which is consistent with a single global thermal reference being physically inconsistent across the dataset's ~4°C / 24°C / 43°C ambient test groups.
7. **Rebalanced loss weights & fixed metric callback:** the data-fit term previously dominated the PDE residual terms 10–100x over, which is consistent with `log_A_sei` never moving from its untrained default and the PDE losses diverging. Loss weights are rebalanced to give the physics terms more relative weight, and the MLflow `MAE_Kelvin_Scaled`/`L2_Relative_Error` metrics — which were flatlined at 0.000 because `train_state.metrics_test` was mostly evaluated on unlabeled PDE points — are now computed directly against the real temperature observations.
8. **Bonus fix — oven abuse test now actually uses the temperature sweep:** the original abuse-test cell computed an ambient temperature ramp (`oven_t_c`, 25→150°C) but never fed it into the model — predictions were made along the ordinary time domain only, so the sweep was dead code. Now that ambient is a real input dimension, the sweep drives the abuse simulation directly.
9. **`A_sei` numerical/gradient-signal fix:** the MLflow run showed `A_sei_value` frozen dead flat at its untrained default for 15,000 steps. Diagnosed root cause: with `Ea_sei = 1.35e5` J/mol, the Arrhenius exponent is around −51 to −54 across the dataset's 0–45°C range — past the old `clamp(min=-50)` guard, making the reaction-rate term ~12+ orders of magnitude smaller than the Joule-heating term it's added to, so its gradient contribution was negligible regardless of loss weighting. The exponent clamp is widened to (−70, 50), and `log_A_sei`'s starting value is now computed diagnostically (targeting rate ≈ O(1) at a representative operating temperature) instead of an arbitrary guess. **Confirmed working:** the actual training run calibrated `A_sei` to 3.44×10²² (`log10 ≈ 22.54`), close to the diagnostic-recommended starting point of 22.88 — a real, moving, converging value instead of a frozen default.
10. **`ic_T` plateau — rebalanced further + added a diagnostic.** The confirmed training run showed `loss_comp_2` (`ic_T`) plateau flat at ~0.849 through the second half of Adam and all of L-BFGS, instead of continuing to decrease — a sign the data-fit term (`observe_T`, weight 20) may be winning a conflict against the `t=0` initial condition rather than both being satisfied. `ic_T`/`ic_c` weights are raised from 5 to 30, and a diagnostic cell after training checks whether `bin=0` (the first downsampled point per cycle) already shows measurable warm-up relative to ambient — which would mean some `ic_T` residual is a genuine data-resolution limit rather than a pure optimization failure.
11. **Medallion ETL (Section 2) marked and gated as one-off.** Bronze/Silver/Gold table creation is now controlled by a `RUN_MEDALLION_ETL` flag (default `False`), so it's skipped on every run after the first instead of needing to be commented out manually. Downstream sections only ever read from the persisted `gold_battery_pinn_database`/`final_pinn_training_data` tables.
12. **Digital Twin Restoration (Section 7) made self-contained, with a `run_id` placeholder.** It no longer silently depends on Sections 4–6 having just executed in the same kernel session — it now redefines every constant, interpolation table, and helper function it needs by re-reading the persisted `final_pinn_training_data` table, so it can run standalone after a kernel restart (as long as the one-off tables already exist). `run_id` is a clearly-marked placeholder that fails fast with a helpful error if left unset, and a missing/legacy checkpoint format now raises an explicit error instead of silently proceeding with wrong physics.
13. **Critical unit bug fixed: `Temperature_measured` is in Celsius, not Kelvin.** The v5 `ic_T` diagnostic (fix #10) surfaced this directly — it printed a bin-0 `(Temperature_measured - ambient)` averaging **≈ −272 K**, which is only possible if one side of that subtraction was in Celsius and the other in Kelvin. The previous `obs_values` formula added `+273.15` to `ambient_temperature` but left `Temperature_measured` unconverted, implicitly treating it as already being in Kelvin. Since NASA's `Temperature_measured` column is in Celsius — same as `ambient_temperature` — this is a pure difference and needs **no** Kelvin conversion at all (the `+273.15` on each side would cancel out algebraically even if both were correctly converted). Fixed in both `obs_values` (Section 5) and the bin-0 diagnostic (Section 6). **`sei_thermal_pde`'s own Arrhenius calculation was already correct** — it only converts the ambient *input* to Kelvin internally and never touches `Temperature_measured` directly, so no PDE code changes were needed, only the training-target formula that `T_delta` is compared against. This bug likely explains a substantial part of the earlier runs' odd behavior (e.g. the `ic_T` plateau, and `T_safe` frequently hitting its clamp floor), since the network was previously being trained against a target offset by roughly −273°C. **Confirmed fixed:** the next training run's bin-0 diagnostic read a sane `mean=0.80°C` instead of `-272K`, and `ic_T` dropped from a 0.849 plateau to `0.00235`.
14. **Abuse-test extrapolation warning.** The Section 7 oven abuse-test sweeps `Ambient` from 25°C to 150°C, but the network's `Ambient` input was only ever trained on `[0, 45]°C` (Section 5's `Hypercube(..., xmax=[..., 45.0])`, matching the dataset's real ~4/24/43°C test groups). Everything past 45°C ambient is the network extrapolating outside its trained domain, which is consistent with the previously-observed non-monotonic SEI-stability curve at high stress (chemical stability appearing to *recover* past ~165°C — a sign of an ungrounded extrapolation, not real chemistry). The plot now visually separates in-domain (solid) from extrapolated (dashed) predictions, prints an explicit warning when the sweep exceeds the trained domain, and restricts the SAFE/WARNING/DANGER status logic to only the in-domain portion of the sweep.
15. **Data-driven danger threshold.** The SEI-stability "chemical failure limit" was a hardcoded `0.985` with no clear grounding. **v8 note:** the first attempt at a data-driven threshold (1st percentile of the model's own in-domain `c` predictions) turned out to be methodologically circular — by definition ~1% of any distribution sits at or below its own 1st percentile, and the actual baseline showed `mean=1.0092`, above the physically valid `[0,1]` range, because the network's raw `c` output isn't clamped the way the internal `c_safe` used in the PDE residual is. Fixed by (1) clipping `c` to `[0,1]` before computing any statistics, and (2) using `mean − 3·std` of the clipped in-domain baseline as the threshold instead of a percentile of the same data — still a heuristic tied to this model's own behavior rather than a literature-validated failure point, but no longer tautological.
16. **DANGER trigger made auditable, and abuse-test data coverage checked.** The verdict previously reported only "DANGER" without saying which condition fired. `core_temp_in_domain.max()` and `sei_health_in_domain.min()` are now printed explicitly against their thresholds. A new diagnostic also checks how much real training data exists near the abuse test's fixed `SoH=0.8, Re=0.5` — satisfying the geometry's bounds doesn't guarantee real data density there, so a DANGER verdict at sparse conditions may reflect an undertrained region rather than real physics.

17. **Held-out battery validation (generalization check).** Every diagnostic up to v8 was checked against the same batteries the model trained on — there was no evidence the model generalizes to a battery it has never seen, as opposed to having simply learned to describe the specific 30 training cells well. Section 3 now splits the 30 target batteries into a 24-battery training set and a 6-battery held-out set *before* `final_pinn_training_data` is built, and a new Section 8 evaluates the trained model against the held-out batteries: temperature MAE/RMSE (train vs. held-out), per-battery error bars, predicted-vs-actual temperature curves, and an SEI-stability baseline comparison. A meaningfully larger held-out error than train error is a direct sign of overfitting to the training batteries rather than learning generalizable battery physics.

18. **Checkpoint corruption fixed (truncated MLflow artifact).** Loading a trained checkpoint intermittently failed with `OSError: Invalid argument` and later `ValueError: negative seek value` from `torch.load`. Diagnosed via a byte-level check: three independent fresh downloads of the same run's artifact all returned identical bytes ending in `\x00\x00\x00\x00` (not a proper ZIP End-Of-Central-Directory record) — ruling out caching/download issues and confirming the artifact stored in MLflow itself was truncated. Root cause: `mlflow.log_artifact` could start reading the checkpoint file before `torch.save`'s write had fully landed on disk. Fixed by writing through an explicit file handle with `flush()` + `os.fsync()` before logging the artifact (Section 6).
19. **Per-battery cycle-survival diagnostic (Section 3).** After the v9 train/held-out split, one held-out battery (`B0056`) silently disappeared from the validation set with no error. Added a diagnostic that prints kept-vs-candidate cycle counts per battery and flags any battery (especially a held-out one) that lost all or most of its cycles, so this kind of silent data loss is caught immediately instead of discovered later as a smaller-than-expected validation set.
20. **Multi-seed ensemble training + abuse-test verdict stability check (new Section 9).** The abuse-test verdict flipped from DANGER to SAFE between two single-run trainings that differed only in a 30-vs-24 battery training set — with identical architecture, hyperparameters, and abuse-test conditions otherwise. That's a sign a single run's verdict may reflect training randomness as much as real physics. Section 6 now trains an ensemble across multiple random seeds (`ENSEMBLE_SEEDS`, default 3), and a new Section 9 re-runs the exact same abuse-test sweep against every seed, reporting the verdict spread (how many seeds say DANGER/WARNING/SAFE) and an overlaid SEI-health plot, instead of trusting one run's number. Section 8 also gained an outlier-battery characterization diagnostic: for any held-out battery with unusually high error, it prints that battery's ambient/SoH/Re/cutoff-voltage values against the training-set range, to distinguish "this battery's conditions are genuinely outside what was trained on" from "the model doesn't generalize well in general."

21. **Local data pipeline (migration off Databricks, step 1).** The raw-to-processed ETL (Section 2's Spark SQL medallion tables and Section 3's feature engineering) is now also available as `python -m battery_pinn prepare-data`, implemented with pandas and NumPy in `src/battery_pinn/etl.py`. It applies the same cutoff voltages, capacity floor, minimum-sample rule, coulomb-counting SoC, SoH, 50-bin downsampling and battery-level train/held-out split, and writes `final_pinn_training_data.csv` / `held_out_pinn_validation_data.csv` (plus the silver and gold tables). Tests execute the original feature-engineering stage against a stub Spark session and assert bit-identical output. Two details worth knowing: (a) the Spark gold join left it unspecified *which* impedance measurement a discharge got when several preceded it (`ROW_NUMBER() ... ORDER BY d.start_datetime` ranked ties arbitrarily); the port deterministically uses the most recent one at or before the discharge. (b) the old per-battery survival diagnostic compared kept *rows* (cycles x 50 bins) against candidate *cycles*, so its "fewer than 20 %" flag could never fire; the port counts cycles on both sides. All paths, table names, battery lists and thresholds that were scattered across the notebook and stage files now live in `src/battery_pinn/config.py`, which the legacy Databricks stages import as well.

22. **Root cause of the missing held-out battery B0056 (item 19), and a capacity floor that no longer deletes whole batteries.** Running the local pipeline on NASA's raw release shows exactly why `held_out_pinn_validation_data` never contained B0056: every one of its 102 discharge cycles was skipped as `low_capacity`. B0056 was cycled at 4 °C with a 2.7 V cutoff (NASA README for batteries 53-56), and at that temperature a healthy cell delivers only 1.11-1.34 Ah before hitting the cutoff -- its *best* cycle (1.344 Ah) is below the 1.4 Ah floor. The floor was not a data-quality guard but NASA's end-of-life criterion (30 % fade of the 2 Ah nominal capacity), which the 4 °C cells can never satisfy. The same floor silently removed B0041, B0045, B0053, B0054 and B0055 (so the "24 training batteries" were in fact 19), left held-out B0047 with 11 of 72 cycles, and was also stricter than its stated intent for the room-temperature cells (1.4 Ah is 25 % fade for B0005, whose best cycle is 1.856 Ah). Fix: the floor is now `min(MIN_VALID_CAPACITY_AH, MIN_CAPACITY_FRACTION_OF_MAX x best cycle of that battery)` (`config.capacity_floor`): a cycle is kept if it clears the nominal end-of-life capacity *or* has faded less than 30 % from what that battery actually delivered. This is a pure loosening -- it never drops a cycle the old rule kept (B0036's outlier best cycle of 2.444 Ah would otherwise have tightened its floor to 1.71 Ah) -- and `MIN_CAPACITY_FRACTION_OF_MAX = None` restores the old rule exactly. On the real dataset kept cycles go from 1466 to 2257 (of 2694), every designated battery now has data (B0056: 101/102, dropping only its aberrant 0.785 Ah first cycle; B0047: 48/72), and the split is a real 24/6. The aberrant near-zero-capacity runs NASA mentions are still dropped. Per-battery before/after: B0005 124->163, B0006 109->109, B0007 168->168, B0018 104->132, B0025 28->28, B0026 27->28, B0027 28->28, B0028 28->28, B0029-B0032 40->40, B0033 118->175, B0034 74->189, B0036 196->196, B0038 35->35, B0039 33->35, B0040 33->33, B0041 0->22, B0042 56->65, B0043 54->65, B0044 49->65, B0045 0->16, B0046 17->43, B0047 11->48, B0048 14->68, B0053 0->55, B0054 0->101, B0055 0->101, B0056 0->101. Alongside: `prepare-data` now reports kept and dropped cycles (by reason, with the floor and best cycle) for *every* designated battery, including ones absent from the metadata, and stops with a `BatteryCoverageError` before writing anything if a held-out battery is missing or has no surviving cycles; `load_dataset` prints the same kind of per-battery report for the processed tables and `evaluate` fails the same way if the held-out file lacks a designated battery (`--no-battery-check` for synthetic data). `battery-pinn convert-mat` turns NASA's `.mat` files into the raw CSV layout, so the whole chain runs from the official download.

23. **Hardening: near-duplicate interpolation breakpoints, explicit compute device, cross-platform CI.** (a) `torch_interp` divided by the gap between neighbouring breakpoints with only a `1e-12` guard. The pooled representative profile takes its `Time_normalized` breakpoints from every cycle, so two values one float32 ulp apart are routine; at the ends of the range that produced extrapolation slopes of order 1e6 and a value of about -1e6 at `t=0`, exactly where the initial-condition collocation points sit (previously noted as a known limitation and worked around by giving the synthetic data an exact shared grid). Breakpoints closer than `MIN_RELATIVE_SPACING` of the range (never less than a few ulps) are now treated as coincident: a step inside the gap, and edge slopes taken to the nearest well-separated breakpoint (constant extrapolation if none exists). The implementation is pure tensor arithmetic, so the PDE residual still performs no host/device synchronisation. (b) `train --device auto|cpu|cuda` (`battery_pinn.device`): `auto` picks CUDA only when PyTorch reports it *and* a probe op succeeds, `cuda` falls back to the CPU with a warning instead of crashing, and the choice is installed as PyTorch's default device because DeepXDE otherwise puts everything on whatever accelerator it detected at import (including Apple MPS, which is never auto-selected now). Checkpoints are saved as CPU tensors. (c) GitHub Actions runs the suite on Ubuntu, Windows and macOS (Python 3.12, plus 3.10 on Ubuntu) with CPU-only PyTorch, and once without PyTorch/DeepXDE; the test session pins the default device to the CPU.

24. **Baseline on the real data: legacy 1.4 Ah floor (19/5) vs corrected dynamic floor (24/6), three seeds each (`docs/RESULTS.md`).** Equal, reduced budget (Adam 1000 iterations, no L-BFGS, `num_domain` 5000; the notebook's 15000 + 2000 L-BFGS takes about 10 h per seed on a 4-core CPU because the residual is evaluated at every observation anchor). Train MAE 11.4 ± 2.0 -> 9.6 ± 1.4 °C, held-out MAE 8.7 ± 2.1 -> 6.6 ± 1.3 °C; on the five batteries held out by both runs the per-battery errors are within the seed spread, and the dynamic run additionally covers B0056 (1.7 °C MAE) -- the corrected floor adds coverage without costing accuracy. Both runs are under-trained (`log10 A_sei` still at its initial 22.88; B0030 at 43 °C ambient has a 22 °C error in both); the legacy verdict flips across seeds (1 DANGER / 2 SAFE), the dynamic one is 3 SAFE. `scripts/run_baseline.sh` reproduces the experiment (any budget) and `scripts/make_results_table.py` compiles checkpoint metrics, per-battery errors and the verdict spread of any set of runs into `docs/RESULTS.md` / `RESULTS.json`; `prepare-data` gained `--min-capacity-fraction FRACTION|none` and `--allow-missing-held-out` so the legacy split can be regenerated deliberately.

25. **Training that converges on a CPU, loss-term logging, and an A_sei identifiability check.** (a) Profiling showed the per-iteration cost is not the network but the collocation set: DeepXDE runs the PDE residual (Jacobian + Hessian) on every input point, and `anchors = all observation points` put the 86k-row table into each step twice (as anchors and as the `PointSetBC` data points), ~2-3 s per Adam step. `train --anchor-subset N` (opt-in) uses a seeded random subset of N observation points as anchors *and* data-fit points; the hardened `torch_interp` from item 23 also turned out ~40x faster than the original on the 82k-breakpoint pooled profile. `--num-initial` adds explicit t=0 points (the notebook relied on the ~1 % of random points with t <= 0.01; an empty IC set gives a NaN loss on which DeepXDE silently stops). A failing L-BFGS line search (PyTorch raises on non-finite losses) no longer aborts the ensemble: the Adam weights are restored and `lbfgs_error` recorded. (b) A `LossTermLogger` callback writes the five weighted loss terms and log10(A_sei) every `--display-every` steps to `loss_history_seed<k>.csv`; the final terms, their shares and the dominant term go into `train_summary.json` and `docs/RESULTS.md`. (c) `battery_pinn.identifiability` classifies an ensemble's final log10(A_sei) values as stuck / seed-dependent / identifiable / merely consistent, and `train --a-sei-init-spread D` starts the seeds D decades apart so that agreement means something; `train_ensemble` writes `identifiability.json`. Result on the real data: with `--anchor-subset 2000`, 2000 Adam + 200 L-BFGS iterations (6-15 min per seed on a 4-core CPU) the corrected 24/6 tables reach train MAE 1.86 ± 0.02 °C and held-out MAE 4.73 ± 0.14 °C (B0030: 22 -> 2.7 °C), against 9.6 / 6.6 °C for the 1000-iteration full-anchor run. The converged loss is 94 % data term; the SEI residual is zero because `A_sei` collapses: seeds started at log10 21.9 / 22.9 / 23.9 ended at 14.7 / 20.3 / 16.5 with identical fits, i.e. **A_sei is not identifiable from surface-temperature data** -- the optimiser switches the SEI reaction off rather than calibrating it, and the SEI half of the abuse-test verdict (SEI min 0.27 ± 0.39, 1 WARNING / 2 SAFE) inherits that arbitrariness. The earlier runs' apparent cross-seed agreement (22.85 ± 0.03) was A_sei never leaving its initial value.

26. **Validation of the local pipeline against the Databricks baseline (`docs/RESULTS.md`, `scripts/run_validation.sh`).** Three additional runs on the corrected 24/6 tables: `seeds5` (five seeds at the converged 2000 + 200 budget with `--anchor-subset 2000`), `fullanchor` (seed 0, same protocol, all 85900 observation points as anchors -- the notebook's choice) and `fullbudget` (seed 0, the notebook's 15000 + 2000 budget and 5000/1000 collocation points, with the subset). 27. **Databricks v9 reference, physics-option grid, fixed-A_sei retrains, ten-model abuse ensemble, CLI clean-up.** `docs/RESULTS.md` now opens with the Databricks v9 reference figures (train 1.2 °C, held-out 7.65 °C; B0025 4.2, B0030 1.1, B0036 11.4, B0042 0.9, B0047 7.3 °C) next to every local run per battery, followed by per-battery and per-ambient error tables.
